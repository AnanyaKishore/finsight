# FinSight — Design Decisions Log

A running log of choices that differ from (or sharpen) the submitted proposal,
and of baseline-repo behaviour we deliberately do **not** copy. Each entry has
the rationale you can defend in the viva. New entries are appended per day.

---

## Part A — Changes to the proposal (and why)

| # | Proposal said | We do | Why |
|---|---|---|---|
| D-01 | Backfill **6 months** of prices | Backfill **12 months** (`ingestion.price_backfill_days: 365`) | A 100-day lookback + 14-day horizon on ~125 trading days leaves only ~12 training windows per ticker. 12 months (the MarketStack free-plan maximum) gives ~137 windows per ticker for the **same quota cost** (1 request per ticker). Lookback and horizon stay exactly as proposed. |
| D-02 | MarketStack, "runs daily incrementally" | MarketStack stays primary; **quota ledger + yfinance fallback** | Free plan = 100 requests/month and *every ticker counts as one request*. 10 tickers × ~21 trading days = 210 > 100. The ledger refuses calls that would exceed `budget − reserve`; the run then degrades gracefully to yfinance and every bar records its `source` (lineage). |
| D-03 | "News from a news source" | **Finnhub** company news | The baseline's NewsAPI free tier only returns the last ~30 days, so a 6-month backfill is impossible. Finnhub's free tier returns ~1 year of company news at 60 calls/min. |
| D-04 | DVC remote (your assignments used **S3**) | **Local DVC remote** (a directory outside the repo); MinIO optional | Guidelines §III: "Cloud Platforms: Not Allowed"; the proposal also promises "no cloud platforms are used". A local remote is the option shown in the DVC lecture. If you want to keep the S3 *workflow*, a self-hosted MinIO container is S3-compatible and is not a cloud platform. |
| D-05 | "Scheduled ingestion container", "the scheduler" | **APScheduler**-based Python service (Day 7), not Airflow | The baseline's Airflow stack (Postgres + Redis + Celery workers + webserver) needs ~2–3 GB RAM; on an 8 GB laptop it would not fit next to Spark, MLflow, DistilBERT and Grafana. Airflow is not in the guidelines' stack; DVC is the mandated pipeline/CI tool. |
| D-06 | Ray (in guidelines' stack) | **Not used**; Spark (local mode) is the data-engineering engine | The rubric asks for "Ray **or** Spark **or** Kubernetes". Spark in `local[4]` mode with a 1 GB driver fits the 8 GB budget; a Ray cluster would compete for the same memory without adding a capability we need. |
| D-07 | LSTM "predicts the next 14 days" | **Direct multi-output** LSTM (one forward pass → 14 values), one **global** model across tickers, **per-window** MinMax scaling | Recursive 1-step forecasting (baseline) compounds its own errors over 14 steps. Per-window scaling (fit on the 100-day input only) removes look-ahead leakage and lets one model learn from all 10 tickers (10× data). |
| D-08 | Registry "Staging and Production" | Classic **stages** *and* **aliases** (`@staging`, `@production`) | Newer MLflow versions recommend aliases and are deprecating stages (Lecture 3, §4.3). We set both: aliases are what the serving containers load; stages keep the UI view the proposal describes. |
| D-09 | Portfolio Sharpe "against an equal-weight baseline" | Report it in sample **and** in a **walk-forward** out-of-sample backtest (weekly re-optimisation on the trailing 30 days, held for the next 5, over the whole year) vs equal weight and minimum volatility | Equal weight (0.1 each) is itself a grid point, so the in-sample optimum can never lose to it — that comparison alone is meaningless. The walk-forward test answers the real question: does optimising on the last 30 days help *afterwards*? |
| D-11 | DistilBERT-SST-2 "classifies company news as positive or negative … converted to a −1 to +1 score" | Same model, unmodified, at a **pinned Hub commit**; score = **p(positive) − p(negative)**; a **neutral band** calibrated on labelled financial sentences; measured on **Financial PhraseBank** before use | SST-2 is movie reviews: whether it transfers to finance is an empirical question, so it is measured (accuracy, macro-F1, vs a majority baseline) on half of PhraseBank, the other half calibrating the band. p_pos − p_neg is continuous through 0 (label × confidence is not: it jumps from −0.5 to +0.5), so weekly averages are meaningful. Much financial news is factual, which the binary model cannot express without a neutral band. |
| D-12 | Grid search with long-only weights | The full lattice (**all 92,378** portfolios at 10 % steps, evaluated exactly), plus a **SciPy SLSQP** check and a **min-volatility fallback** | The baseline sampled random weights. The exhaustive grid is deterministic and takes ~0.1 s vectorised. SLSQP measures what the 10 % resolution gives up. If no portfolio beats the risk-free rate, maximising Sharpe would pick the *most volatile* one, so the optimiser falls back to minimum volatility and says so. |
| D-10 | Python version unspecified (q4demo used 3.14) | **Python 3.11** everywhere (mamba env, Docker, MLproject) | PySpark, PyTorch-CPU and MLflow all ship stable 3.11 wheels; one version everywhere is what "environment parity" means. |

| D-13 | One sentiment model (DistilBERT-SST-2) | DistilBERT stays the default; **FinBERT** is registered as a **challenger** and the promotion gate decides on a dataset **neither model was trained on** (Twitter financial news) | Day 4 measured weak transfer from movie reviews (PhraseBank binary accuracy 0.681 vs 0.654 majority). FinBERT is a natural candidate, but it was fine-tuned *on PhraseBank*, so comparing the two there would be test-set leakage. Keeping the proposal's model as the tie-breaking default and letting measured evidence pick the production model is the champion/challenger practice the registry exists for. |

## Part B — Baseline behaviour we deliberately do NOT copy

Found while reviewing `MLOps_AI_App` and `MLops_AiApp_rnn_model_tracking`:

1. **`/api/prediction/{ticker}` returns synthetic numbers.** `Web App/app.py` builds the forecast from a seeded random slope plus noise; the stored LSTM predictions are ignored. FinSight serves real model output (or clearly labelled last-known output when degraded).
2. **API keys committed in source** (`stock_data_config.py`, `stock_data_dag.py`). FinSight keeps secrets only in a git-ignored `.env` (encrypted copy on Day 9).
3. **Scaler fit on the whole series** in training (leaks future min/max into the past). Fixed by per-window scaling (D-07).
4. **Inference reads the *oldest* 100 days**: `find(...).sort("date", 1).limit(100)`. FinSight always takes the most recent window.
5. **Validation split yields no windows**: 30 validation days with a 100-day sequence length produces zero validation sequences.
6. **Frontend served by the Flask backend** (`render_template`), i.e. not loosely coupled. FinSight's frontend is a separate container that calls the backend only through a configurable REST base URL (rubric: "strictly follow loose coupling").
7. **Duplicate inserts** in historical backfill (`insert_many` without a unique key). FinSight uses unique indexes and upserts everywhere.
8. **Monitoring stack commented out** in the root compose file, and only infrastructure metrics (node/Mongo). FinSight instruments the application, pipeline and model quality.

## Part C — Day-by-day decisions

### Day 1 (21 Oct)
- **One ingestion code path.** `incremental` gap-fills from each ticker's last stored date and falls back to the backfill window when a ticker has no data, so missed days self-heal.
- **Skip tickers that are already current** using a NYSE trading calendar (`latest_expected_session`), because an empty MarketStack response still costs quota.
- **Empty provider response = failure** when the range must contain a trading session (yfinance returns an empty frame instead of raising when Yahoo is unreachable — found during testing).
- **Retry policy:** exponential backoff with full jitter; only network errors, 429 and 5xx are retried; quota errors are never retried.
- **Idempotency:** unique indexes `(ticker, date)` and `(ticker, news_id)` + bulk upserts.
- **Structured JSON logs** with a `run_id` on every line of a run, to be surfaced in the pipeline console.
- **Bug found by the integration tests (real MongoDB):** upserts stamped `updated_at: now` in `$set`, so an identical re-upsert was counted as a revision (`modified_count` 2 instead of 1). mongomock did not expose it. Fixed by keeping only data fields in `$set` (`ingested_at` remains as first-seen lineage); the unit test now asserts `updated == 0` on an identical rerun. This is the case for keeping both unit tests (fast, mocked) and integration tests (real services) in the test plan.

### Day 2 (22 Oct)
- **pandas pinned to 2.3.3** (was 3.0.6): PySpark 4.2 warns that pandas ≥ 3 is not fully supported.
- **The export writes microsecond timestamps.** pandas defaults to nanoseconds, which Spark rejects (`PARQUET_TYPE_ILLEGAL: TIMESTAMP(NANOS)`). Caught by the Spark end-to-end unit test before it reached the real pipeline.
- **Deterministic outputs everywhere** (sorted rows, no bookkeeping fields, no timestamps in manifests, Spark part files renamed to `part-00000.parquet`, side files removed). Verified in a rehearsal: a second `dvc repro` re-runs `export` but skips `validate` and `process`; changing one `etl` param re-runs only `process`.
- **Tests gate the data.** `export` depends on `reports/unit_tests.json`, so a failing suite stops `dvc repro` before any data moves (verified with a deliberately failing test). `process` depends on `reports/data_quality.json`, so Spark never runs on data that failed a blocking check (verified with an impossible threshold).
- **Custom expectation suite instead of the `great_expectations` package**: same concepts (expectations, suite, severity, persisted report, fails on known-bad data), without a heavy dependency tree. Blocking vs warning severities are separated so a few missing days or a genuine market shock never halt the pipeline, while schema breaks, duplicates or an unadjusted split always do.
- **Model price rule**: `adj_close` per ticker only if complete, else `close`. Never mix the two in one series.
- **Calendar alignment with a broadcast join** (small calendar table shipped to executors), bounded forward-fill (≤ 2 days, flagged `is_filled`), and features that stay null until a full window exists.
- **Spark sizing**: `local[4]`, 1 GB driver, 8 shuffle partitions, adaptive execution off (stable plans and output layout). JVM start-up is reported separately from processing time.
- **Throughput is reported honestly**: on ~10k rows, Spark's fixed overhead dominates (~1.7k rows/s in the rehearsal). `finsight.etl.benchmark` shows throughput rising with volume (rehearsal: about 1.7k → 9.5k → 18.7k rows/s at 1×/10×/50×). This is the argument for Spark at scale, and the reason it is not "faster than pandas" at 10k rows.
- **Run records** (`pipeline_runs`, `pipeline: "dvc"`, one per stage) are written best-effort: if MongoDB is down, the stage still runs and only a warning is logged.
- **Docker base pinned to `python:3.11-slim-bookworm`** for the `openjdk-17-jre-headless` package (newer Debian releases dropped Java 17). The pipeline image runs Spark from Day 7 (scheduler), and the image is rebuilt and checked then.
- **Real-data finding: zero prices from MarketStack.** The first real `dvc repro` stopped at `validate`: 3 stored bars had a price of 0, which produced 4 infinite log returns. The gate did its job, since without it Spark and the LSTM would have trained on infinities. Fixes:
  - (a) a single boundary sanitiser (`make_price_bar`) used by every price provider: it rejects close ≤ 0, nulls adj_close ≤ 0, and repairs non-positive open/high/low and negative volume;
  - (b) `ingestion repair [--dry-run]` re-fetches each invalid stored bar from the unmetered fallback, storing raw close with `adj_close = None` so two providers' adjustment factors never mix; if nothing comes back it deletes the bar, and the ETL forward-fills the gap. Repairs are recorded as `ingestion` runs with `mode = "repair"`;
  - (c) `prices.positive_values` now lists the offending rows plus the fix command, and non-positive prices are masked before return calculations, so one bad bar is reported once, not three times.

### Day 3 (22 Oct, ahead of schedule)
- **One global LSTM, per-window MinMax scaling, direct 14-step output, residual to the last price.** About 139 windows per ticker is too few for 10 separate models; per-window scaling (fitted on the 100 input days only) removes the baseline's look-ahead leakage and puts all tickers on one scale. The zero-initialised residual head makes an untrained model exactly the naive forecast, so training only moves away from naive where the data supports it.
- **Purged chronological split** per ticker: train | 14-window gap | val (15) | 14-window gap | test (15). No training target overlaps a validation or test target. The selected configuration is refit on train+val for the early-stopped number of epochs; test is touched only by `evaluate_lstm`.
- **Selection by validation MAPE** (scale-free across tickers), not pooled RMSE, which the most expensive stocks would dominate.
- **Honest baselines**: naive (last price) and drift. Skill = 1 − MAPE_model / MAPE_naive. Beating naive on daily prices over 14 days is hard; the comparison is reported, never hidden, and the Day 5 promotion gate uses it.
- **Lineage beyond autolog**, as tags on every run: git commit + `git_dirty_code` (DVC-generated paths excluded), DVC hash of `data/processed/prices`, export snapshot SHA-256, seed, library versions, platform. Also logged: the dataset (`mlflow.log_input`), `params.yaml`, `dvc.lock`, the data-quality report, per-configuration learning curves (child runs), the selection table, and the test verdict (`beats_naive` tag). `models/lstm/run.json` plus `reports/lstm_train.json` link the Git commit to the MLflow run ID.
- **Bug found by tests**: `git status --porcelain` output was stripped, cutting the first character of the first path, so runs would have been tagged dirty even when the code was clean.
- **Packaged as MLflow "models from code"** (`pyfunc_entry.py`) instead of a pickled object: loading never unpickles code, and weights load with `torch.load(weights_only=True)`. Preprocessing lives inside the model (same `scale_rows` as training), so callers send raw prices: no training/serving skew. The signature is enforced by MLflow, so malformed requests are rejected before reaching the network.
- **Determinism verified**: a forced retrain (`dvc repro -f train_lstm`) reproduced identical test metrics. This holds for the same thread count on the same machine; across CPUs, floating-point results can differ in the last digits.
- **MLproject uses `conda_env: environment.yml`**: the exact environment file the developer uses (which pins `requirements/*.txt`), so dev and test environments are identical by construction. Entry-point parameters are named `*_override` because MLflow parameters are immutable and the code logs the resolved values itself.
- **MLflow server**: own Dockerfile pinned to the client version (3.17.2); SQLite backend plus `--serve-artifacts` (clients never need a shared filesystem); `--allowed-hosts` allows only localhost and the compose service name (MLflow 3's DNS-rebinding protection); bound to 127.0.0.1.
- **CPU-only PyTorch** from PyTorch's CPU wheel index (`requirements/ml.txt`). The PyPI build pulls about 2+ GB of CUDA libraries that this machine cannot use.
- **pyarrow pinned to 25.0.1** (mlflow 3.17 requires < 26).
- **MLflow server memory (found on the real laptop, Day 3).** The container was OOM-killed (exit 137) at 512 MB. MLflow 3.17's server starts, besides the web worker, a job runner and 7 `huey` consumer processes for GenAI evaluation/trace jobs, about 1.7 GB in total. Fixed with `MLFLOW_SERVER_ENABLE_JOB_EXECUTION=false` (measured ~510 MB steady, 514 MB peak while a training run uploads artifacts) and `mem_limit: 768m`. The memory budget in PROJECT_PLAN.md was updated (≈ 6.1 GB peak).

### Day 4 (23 Oct)
- **Sentiment model is downloaded once, at a pinned commit, by a DVC stage** (`fetch_sentiment`): `distilbert-base-uncased-finetuned-sst-2-english@714eb0fa…` and Financial PhraseBank `@8d3fe0c3…`. Both are DVC-cached outputs, so every later stage and machine works offline and byte-identically. PhraseBank's Hub loading script no longer works with current `datasets` versions, so the raw ZIP is parsed directly (no `datasets` dependency).
- **Evaluate before use** (`evaluate_sentiment`): seeded, stratified 50/50 split of PhraseBank (AllAgree, 2,264 sentences). The calibration half chooses the neutral band (highest 3-class macro-F1; ties → smaller band); the test half is used only for reporting. Binary (pos vs neg) and 3-class metrics, each against a majority-class baseline, plus latency p50/p95 and the 10 most confident mistakes (error analysis) are logged to MLflow (`finsight-sentiment`).
- **Packaged like the LSTM**: MLflow models-from-code pyfunc (`text` → `label`, `confidence`, `score`) with the Hugging Face directory and a `config.json` holding the calibrated band as artifacts, so serving applies exactly the evaluated rule. `model_version` = base commit + band + max length.
- **Incremental scoring** (`score_sentiment`): the score cache is a `persist: true` DVC output keyed by `(ticker, news_id, text SHA-1, model_version)`. Daily runs score only new or edited articles; a new model version or band re-scores everything automatically. Texts are length-sorted before batching (similar padding per batch); scores are rounded to 6 decimals, and tests prove they do not depend on batch size or order.
- **Explainability for sentiment**: each weekly bar carries its top-3 positive and top-3 negative headlines (with scores and source links). The portal shows *why* a week is negative, not just that it is.
- **Results published to MongoDB** (`news_sentiment`, `sentiment_weekly`, `portfolios`) by the DVC stages themselves, with idempotent upserts plus removal of stale documents. DVC outputs stay the source of truth; after a Mongo reset, `dvc repro -f score_sentiment optimize_portfolio` restores the published copy.
- **Portfolio inputs**: simple daily returns of the last 30 aligned trading days (dates where any ticker is missing are dropped), annualised ×252; risk-free rate is a tracked param (3-month T-bill, ~3.9 %).
- **LSTM explainability: occlusion attribution** over the 100-day window, run through the packaged pyfunc model on the test windows (`reports/plots/lstm_input_attribution.csv`, MLflow). Each 10-day block is replaced by a straight line between its neighbours, and the forecast change is measured. Expected for a near-naive model: almost all sensitivity in the last block (rehearsal: 3.9 % vs ≤ 0.09 % for older blocks).
- **Feature-impact experiment** (volatility as a second LSTM input), logged to `finsight-lstm-experiments` only: identical windows, the selected configuration, 3 seeds, decision on **validation only**. Rule: recommend only if the gain exceeds 2 × the seed standard deviation. In the rehearsal, a 1 × rule "found" an improvement on synthetic random-walk data, where none can exist, so it was tightened. The network gained an optional `input_size`; the default reproduces the Day 3 model bit-for-bit (verified: the forced retrain matched the committed Day 3 metrics exactly).
- **`train_lstm` depends only on model-shaping code** (data, network, metrics, pyfunc, train, tracking) and on `lstm` params. Analysis settings moved to `lstm_explain`, so editing evaluation or explanation code never retrains the model.
- **Test-only shim extended**: pymongo 4.19 passes `sort=` to `add_replace` too (used by `ReplaceOne`), which mongomock 4.3 rejects.
- **Memory**: full-size DistilBERT inference peaks at about 1.3 GB RSS (measured with a randomly initialised model of the same architecture). DVC runs stages one after another, so it never overlaps Spark (1 GB driver) or LSTM training.

**Day 4 real results (laptop, 23 Oct, data to 22 Oct):**
- **LSTM** test MAPE 2.9156 vs naive 2.9122 (skill −0.1 %), within the 2 % acceptance band. Directional accuracy 0.600, but 60 % of test moves were up, so this is not a directional edge. Occlusion: hiding the last 10 days moves the forecast 3.32 %; any older block ≤ 0.07 %. Volatility as a second input made validation worse (−0.015 MAPE), so it is not recommended. The selected configuration changed from Day 3 (now h32-l1-lr0.003) after one extra trading day, which shows how flat the grid is.
- **Sentiment** (DistilBERT, PhraseBank AllAgree test half, 1,131 sentences): binary accuracy 0.681 / macro-F1 0.681 vs majority 0.654 / 0.395; 3-class macro-F1 0.540 vs 0.254; neutral band 0.9928 (the model is near-certain on almost everything). Articles: 66 % neutral, 22 % negative, 13 % positive, mean −0.20, a known negative tilt of SST-2 models on factual text. Latency p50 37 ms. First full scoring 11,015 articles in 9.8 min (18.8/s).
- **Portfolio** (as of 22 Oct): in-sample max-Sharpe 7.71 vs equal weight 1.84, but **out of sample** (weekly walk-forward over the year) Sharpe 0.12 vs equal weight 0.60 and min-volatility 0.31. A 30-day estimation window overfits; the grid gives up only 0.045 Sharpe to SLSQP.

### Day 5 (24 Oct)
- **Registry gate (`register` DVC stage).** Registers each new LSTM version and every sentiment candidate (idempotent: one version per MLflow run, so re-running the stage registers nothing). Promotes only on acceptance plus a strict improvement over the champion **on the same data**: the LSTM champion is re-scored on today's test windows; the sentiment champion is re-evaluated if its evaluation fingerprint (dataset revision, split share, seed) differs. Both aliases (`@production`, `@staging`) and classic stages are kept (D-08); stages are best effort because MLflow 3 deprecates them.
- **Bootstrap rule**: with no production model yet, the best candidate is promoted so the system can serve, and the decision records whether it passed acceptance. This is visible in `reports/promotion.json` and `/api/model-info`.
- **Rollback** tags the bad version `rolled_back`, so the gate never re-promotes it automatically. An operator explicitly restoring it with `--to-version` clears the mark. The command updates `reports/promotion.json`, so the next `dvc repro` re-runs everything that depends on the production model. Rehearsed end to end: rollback → `dvc repro` (register keeps the rolled-back-to version, score_sentiment re-scores) → restart → served version changes.
- **Production pointer instead of hard-coded folders.** `score_sentiment` resolves the production model from `reports/promotion.json`. It uses the local packaged copy when that is the production run, and otherwise downloads the exact registered version into `models/registry_cache/`, so a rollback to an older version scores with the right weights.
- **Sentiment evaluation is per candidate** (`foreach` DVC stages). The gate dataset is the Twitter financial-news validation split (2,388 headlines, MIT, URLs stripped). PhraseBank is still reported, flagged `contaminated` for FinBERT. The scorer handles 2- and 3-label models; the score stays P(pos) − P(neg) and confidence is the top-class probability, now cached per article (Day 4 caches are back-filled exactly, since they were all 2-label).
- **Bug found in rehearsal against a real MLflow server**: `MlflowClient.create_model_version(source="models:/m-…")` works against a local SQLite store (unit tests) but the REST registry rejects it without `model_id`. Switched to `mlflow.register_model`, which resolves MLflow 3 logged-model URIs. Model version numbers come back as `int` from some stores and `str` from others, so the registry code normalises them to strings (caught by a test).
- **Serving**: one image (`docker/Dockerfile.serve`), two services running `mlflow models serve -m models:/<name>@production --env-manager local`. The registry URI is resolved at start-up, so promotions and rollbacks need a restart, never a rebuild. Both are bound to 127.0.0.1 and run as non-root, with HF offline mode.
- **Measured serving memory** (rehearsal): `mlflow models serve` keeps a ~250 MB launcher process next to the uvicorn worker. LSTM ≈ 0.9 GB in total, sentiment ≈ 1.1 GB with a tiny model; DistilBERT adds ~0.27 GB and FinBERT ~0.44 GB. Limits set to 1 GB and 2 GB (the earlier plan of 512 MB / 1.2 GB would have been OOM-killed).
- **Backend** (FastAPI): every route has typed request/response models (the LLD's I/O spec, also exported as `docs/api/openapi.json`), a uniform JSON error envelope with stable codes, request IDs, CORS restricted to the frontend origin, and Prometheus metrics labelled by route *template* (bounded cardinality). The image contains only `common` + `api` and their dependencies (verified: the app starts in a clean environment with `requirements/api.txt` alone, without pandas or torch).
- **Forecasts are stored** (`forecasts`, one per ticker / origin / model version): repeated requests reuse one model call (rehearsal: 50 ms vs a model round-trip), and Day 8 compares the stored forecasts with realised prices. If `lstm-serve` is down, the latest stored forecast is served with `stale: true`; with no stored forecast the API answers 503.
- **`.dockerignore` added** (missing since Day 1): the build context no longer includes `.env`, `data/`, `models/` or `.git`, which is a secret-leak and build-speed fix.

### Day 6 (26 Oct)
- **Portal without a build step.** Plain HTML, CSS and ES-module JavaScript served by nginx, instead of React/Vite or Streamlit. Nothing to compile, no Node.js on the laptop or in CI, an image of ~80 MB that uses ~4 MB of RAM (both measured), and the UI stays a pure REST client of the backend (loose coupling, as the rubric asks). Streamlit, used by the baseline repos, would have needed a Python server process for the UI.
- **Runtime configuration.** The browser needs the backend's address, so nginx generates `/config.js` from `BACKEND_URL` when the container starts (envsubst template). One image serves any backend; moving the API means changing an environment variable and restarting, never rebuilding. The same variable feeds the Content-Security-Policy `connect-src`, and a start-up script rejects anything that is not a plain http(s) URL.
- **Chart.js vendored, not loaded from a CDN.** The proposal says no cloud platforms; a self-hosted portal should not depend on a third-party host at run time either. Chart.js 4.4.7 (MIT) is committed under `frontend/assets/vendor/` with its licence.
- **Chart rules.** No dual axes: weekly article counts get their own small chart under the sentiment bars rather than a second y-axis. The forecast is dashed (the usual "projection" cue) and joined to the last real price. Sentiment bars are coloured by sign but also sit above or below the zero line, so colour is never the only cue; the overview change has an arrow and a sign as well as green/red. Every chart has a tooltip and a table view.
- **Honesty in the UI.** The forecast caption quotes the registered model's back-test MAPE next to the naive baseline's (from the registry tags via `/api/model-info`), and the portfolio card shows the walk-forward result against equal weight. The proposal's metrics are displayed where a user makes sense of them, not only in MLflow.
- **New endpoint `GET /api/stocks`.** The overview lists all ten stocks; abusing `/api/search` with a one-letter query would not return them all. CORS now allows `127.0.0.1:8080` as well as `localhost:8080` by default, because browsers treat the two as different origins.
- **Serving image built once.** `sentiment-serve` no longer has its own `build:` section; it reuses the `finsight/serve` image that `lstm-serve` builds (`pull_policy: never`). Two build sections for one tag made Compose build it twice and leave a ~2 GB untagged image behind (seen on Day 5).
- **Resumable sentiment scoring.** The Day 5 FinBERT re-score ran for about an hour with no output, and an interruption would have lost everything. Scoring now runs in chunks of `sentiment.checkpoint_every` (500) articles, shortest first; after each chunk it logs progress with a time-left estimate based on characters (an articles-per-second estimate is far too optimistic when the longest texts come last) and writes `article_scores.partial.parquet` atomically. The next run merges the checkpoint into the cache, so it resumes; the checkpoint is removed when the stage succeeds. `checkpoint_every` is deliberately not a DVC param, because it does not change the output (tested: chunked and one-shot results are identical).
- **Not done (offered on Day 5): truncating FinBERT input to 128 tokens.** It would roughly halve a full re-score, but it changes the model fingerprint, so it must go back through the gate. Daily runs only score ~50-100 new articles, so it is not worth it now.

### Day 7 (27 Oct)
- **A small scheduler service instead of Airflow, cron or Ray.** The baselines use Airflow; on an 8 GB laptop its scheduler, webserver and metadata database would cost more memory than the pipeline itself, and the DAG already exists in `dvc.yaml`. A ~600-line Python service in the existing pipeline image runs the DVC targets, records every step, and exposes a tiny HTTP API. Plain cron would have no catch-up, no "one run at a time" guarantee and nothing for the console to read.
- **Schedule: Tuesday–Saturday 06:30 IST.** US markets close at 01:30–02:30 IST, so a morning run sees the previous US session; Monday morning has no new session (Sunday/Saturday US), Saturday morning picks up Friday's. The check repeats every minute, so a laptop that was asleep at 06:30 runs as soon as it wakes ("catch-up"), and the "already started today" rule means never twice a day. Console runs do not count as the day's scheduled run.
- **Daily runs never retrain.** `score_sentiment` depends on `register`, which depends on `train_lstm`, so a plain `dvc repro score_sentiment` would retrain the LSTM every day. The daily plan runs `dvc repro process` and then `dvc repro --single-item` for scoring and the portfolio. Retraining is the separate "retrain" plan (full `dvc repro`), started by a person or by a drift alert (Day 8), and the promotion gate still decides whether the new model is used.
- **Critical vs non-critical steps.** A failed data step (tests, validation, ETL) stops the run, because everything after it would work on bad data; a failed scoring or portfolio step is recorded and the run ends as *partial*. Ingestion exit code 3 (some tickers failed) is partial, not failed.
- **Steps as child processes with a hard timeout.** Each step runs in its own process group with a time limit from `params.yaml` (`scheduler.timeouts_s`); on timeout the whole tree (DVC → Python → Spark JVM) gets SIGTERM, then SIGKILL. Output goes to `logs/scheduler/<run_id>.log` and the last 40 lines into MongoDB, so a failure can be read in the browser.
- **One `run_id` from run to stage.** The scheduler passes `FINSIGHT_PIPELINE_RUN_ID` to every command; `stage_run` and the ingestion run record store it, so the console drills down from a run to the exact DVC stages it executed, and the run summary (rows/s, articles/s, prices and articles added, model promoted) is computed from those records rather than parsed from logs.
- **The repository is mounted, not copied.** The scheduler runs `dvc repro` in your working copy (`.:/app`), as your user id, so `data/`, `models/`, `dvc.lock` and `reports/` are exactly what you would get by running it yourself, and files stay owned by you. The DVC remote is mounted at the same absolute path so `.dvc/config` works unchanged.
- **Versioning: `dvc push` plus a local commit only.** After each run the scheduler pushes data/models to the local DVC remote and commits `dvc.lock` + `reports/` with a pathspec (your own staged changes are untouched), with `--no-verify` and a recognisable author. It never pushes to GitHub, so no Git credentials enter a container. It skips the commit during a merge/rebase or on a detached HEAD.
- **Triggers go through the backend; the token stays server-side.** The console calls `POST /api/pipeline/trigger`; the backend forwards to the scheduler with `SCHEDULER_TOKEN` (constant-time comparison). The browser never sees the token and the scheduler port is bound to localhost. A missing, placeholder (`replace-me`) or short token disables HTTP triggers rather than accepting a guessable one; scheduled runs still happen. Alertmanager's "resolved" notifications are ignored so a recovering alert does not start a second retrain.
- **Model servers follow `@production` by themselves.** A retrain can move the alias, but `mlflow models serve` loads one fixed version at start-up. Rather than give the scheduler the Docker socket (root on the host), each serving container runs a small watcher (`docker/serve_watch.py`) that resolves the alias, serves that version, checks every 60 s and exits when the alias moves; `restart: unless-stopped` brings it back with the new model. After a promotion the forecasts step waits for `lstm-serve` to go down and come back before storing forecasts.
- **Console reads MongoDB, not the scheduler.** History, run detail, DAG and statistics come from Mongo through the backend, so the console still works when the scheduler is stopped; only the buttons need it. The DAG structure comes from `dvc dag --dot` and the stale markers from `dvc status`, refreshed by the scheduler after every run (the backend has no DVC).
- **DAG diagram drawn by the page, not an image.** A small layered layout (row = longest path from a source, rows ordered by their parents' positions) rendered as SVG: clickable and keyboard-focusable stages, colour plus a word for each status, and an amber dot for "inputs changed". No graph library was needed for 14 stages.
- **Charts.** Duration is one bar per run in minutes, coloured by outcome, with daily and retrain on separate views because a retrain is several times longer and would flatten the daily bars. ETL rows/s and articles scored/s have different units, so they are two small charts, never two axes on one. Both have tables.
- **Memory.** The scheduler container is capped at 3 GB: steps run one at a time and the largest (LSTM training, or Spark with a 1 GB driver) peaks around 2–2.5 GB. With the rest of the stack (~4 GB) that is within 8 GB only because steps never overlap; if the laptop is tight during a retrain, `docker compose stop sentiment-serve` frees ~1.5 GB.

### Day 8 (28 Oct)
- **The monitor lives in the scheduler, not in a new service.** The scheduler already runs every 2 minutes, reads MongoDB and serves `/metrics`, so drift and live error are computed there (every `monitoring.interval_s` and as the "monitor" step of each run) and exported as gauges. A separate monitoring container would cost another ~150 MB for the same work.
- **Prometheus holds the decision, the thresholds live in `params.yaml`.** The report computes `detected` with the configured thresholds and exports it as `finsight_*_detected`; the alert rules fire on those gauges and carry the raw number (PSI share, error ratio) in the message. Changing a threshold is then one edit in `params.yaml`, not two in YAML and PromQL that could disagree.
- **Returns drift: PSI on 60 days vs the year before, 5 bins, +0.5 smoothing.** Prices themselves always "drift" (trend), so the monitored feature is the daily log return, which is what the LSTM's per-window scaling sees. Simulating no-drift data showed the first design (20 days, 10 bins, a 1e-4 floor for empty bins) gave a median PSI of about 1.0, so it would have flagged every stock all the time. With 60 days, 5 bins and additive smoothing the 95th percentile with no drift is 0.19, and a doubling of volatility gives a median of 0.34, so the textbook threshold of 0.25 means something. KS is reported next to PSI because it needs no bins.
- **Retrain only on a market-wide shift.** One volatile stock is news, not a broken model; the retrain alert needs at least 30 % of the stocks above the threshold for 5 minutes.
- **Live error is judged against the naive forecast on the same points.** A 3 % MAPE is good in a volatile week and bad in a calm one. Comparing with "price stays the same" on exactly the realised points (as the promotion gate does offline) removes the market's own volatility. It needs at least 20 realised points and an absolute floor of 3 %, so a few days of data or a tiny error cannot start a retrain.
- **Sentiment shift alerts but never retrains.** The sentiment models are pretrained and selected by the gate; retraining the LSTM would not fix a news-tone change, so `SentimentShift` is informational.
- **Retrain loop protection in two places.** Alertmanager repeats the retrain notification only every 24 h, and the scheduler ignores `/retrain` within 24 h of the last retrain (`200 ignored: cooldown`, counted in `finsight_retrains_skipped_total`). If drift persists after a retrain, the promotion gate has already said the new model is no better, so retraining again every few minutes would only burn CPU.
- **A drift drill instead of corrupting data.** `python -m finsight.monitoring.drill start` stores a flag that makes the monitor scale the recent returns ×4 (and shift sentiment) for a limited time. The whole loop (gauge → alert → Alertmanager → webhook → retrain → gate) runs for real, but no stored price changes, so nothing has to be repaired afterwards, and the report, a gauge and an info alert all say a drill is on.
- **Every component is monitored, with the smallest set of exporters.** The backend and scheduler have their own metrics; cAdvisor covers every container, including MLflow and the model servers that have no `/metrics`; node-exporter covers the host, mongodb-exporter the database and nginx-exporter the frontend (`stub_status` on an internal port that compose never publishes). cAdvisor is limited to the metrics the dashboards use, so Prometheus stays small.
- **Dashboards as code, generated.** Five dashboards (Overview, API, Pipeline, Models & drift, Infrastructure) are written by `scripts/build_dashboards.py` into JSON that Grafana provisions read-only. Hand-exported Grafana JSON is thousands of lines that cannot be reviewed; the generator keeps every panel's query, unit and threshold line in one readable place. Each chart has a dashed threshold line matching its alert.
- **Local only, small footprint, secrets out of files.** All UIs bind to 127.0.0.1; the Grafana admin password comes from `.env` and compose refuses to start Grafana without it; Grafana's analytics and plugin downloads are off. Alertmanager cannot read environment variables, so its entrypoint writes the scheduler token to a file inside the container (mode 600) and the config points at the file. Prometheus keeps 15 days or 1 GB. Together the new services add about 0.5 GB.
- **Backend dependency gauges refresh on scrape.** `finsight_dependency_up` used to change only when someone opened `/api/health`; now each scrape refreshes it (at most every 10 s), so `ModelServerDown` fires even when nobody is using the portal.
